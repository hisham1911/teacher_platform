# ADR 008 — التصحيح الخادمي وسلطة الوقت ومقارنة JSON الدلالية

**الحالة:** Accepted
**التاريخ:** 2026-08-05

## السياق

Phase 4 تتطلب: (1) تصحيح إجابات الطلاب **على الخادم حصرًا** (العميل لا يرى الإجابات الصحيحة)، (2) وقتًا **خادميًا مرجعيًا** لا يمكن للاعب التحايل عليه بتعديل ساعة جهازه، (3) **Idempotency** لإرسال الإجابات (إعادة الإرسال نفسه = نجاح، إجابة مختلفة = 409).

## القرار

### 1. التصحيح الخادمي (`AnswerScorer`)

- دالة نقية في Domain: `AnswerScorer.Score(type, configJson, options, answerJson, points)` — بلا اعتماديات، قابلة للاختبار وحديًا.
- خمسة أنواع: `MultipleChoice`/`TrueFalse`/`Listening` (كل شيء أو لا شيء عبر `optionId`)، `ShortAnswer` (مقارنة بعد `NormalizeText`: FormC + Trim + طي المسافات + lower، مقابل `acceptedAnswers`)، `Ordering` (تطابق كامل = كامل الدرجة، وإلا `(correctPositions/total) × points` مقربًا لمنزلتين AwayFromZero).
- **لا ترمي استثناءات أبدًا** — أي إدخال غير صالح = صفر. إجابة الطالب المشوهة لا يجب أن تسقط الطلب.
- DTO اللاعب الآمن (`PlayerQuestion`) لا يتضمن `IsCorrect` ولا `acceptedAnswers` — الخيارات ترسل بنصها فقط.

### 2. سلطة الوقت الخادمية

- `StartedAt` و`DeadlineAt` يُحسبان على الخادم عند بدء المحاولة؛ كل استجابة تتضمن `serverNow` ليصحح العميل انحراف ساعته.
- **Settle-on-request:** عند أي طلب بعد انقضاء `DeadlineAt`، يُنهي الخادم المحاولة بحالة `TimedOut` ثم يرد — لا مؤقتات خلفية ولا jobs.
- الاستئناف بعد F5: `current-question` يعيد `serverNow` + `deadlineAt` + الفهرس الحالي، فيستعيد العميل العد التنازلي الصحيح.

### 3. Idempotency بمقارنة JSON دلالية

- عمود `AttemptAnswers.AnswerJson` نوعه **`jsonb`** — PostgreSQL يطبّع المخزن (مسافات، ترتيب مفاتيح، تمثيل أرقام).
- لذلك المقارنة النصية الحرفية (`string.Equals` Ordinal) بين المخزن والوارد **تفشل زورًا** وتعيد 409 لإعادة إرسال نفس الإجابة — bug حقيقي اكتشفته اختبارات التكامل.
- **الحل:** `AnswerJsonEquals` في `PlayerService` — مسار سريع ordinal، ثم تحليل `JsonDocument` للطرفين ومقارنة عميقة (`JsonElementDeepEquals`): الأرقام عبر `GetDecimal` (تساوي `1` و`1.0`)، الكائنات بمفاتيح مرتبة ordinal، المصفوفات عنصرًا بعنصر. فشل التحليل = غير متساويين.
- نفس المقارنة تُستخدم في المسارين: الإرسال العادي ومسار الاستشفاء من تعارض التزامن (race recovery).

## البدائل

- **التصحيح في العميل:** يكشف الإجابات الصحيحة في الشبكة/الذاكرة — مرفوض أمنيًا.
- **مؤقت خادمي (BackgroundService) لإنهاء المحاولات:** تعقيد بلا فائدة في MVP؛ settle-on-request يغطي كل المسارات لأن أي تفاعل لاحق يمر عبر الخادم.
- **تخزين AnswerJson كنص `text` بدل `jsonb`:** يحل مشكلة المقارنة لكنه يفقد فهرسة/استعلام JSON ويتعارض مع قرار التخزين المعتمد — فُضّل إصلاح المقارنة دلاليًا.
- **تطبيع JSON عند الكتابة (canonicalization):** هشّ — أي اختلاف تمثيل من العميل يكسره؛ المقارنة الدلالية أقوى.

## النتائج

- الإجابات الصحيحة لا تغادر الخادم أبدًا قبل الإنهاء.
- تعديل ساعة الجهاز لا يمنح وقتًا إضافيًا.
- إعادة إرسال الإجابة نفسها (شبكة متقطعة، نقرة مزدوجة) آمنة تمامًا؛ التغيير الفعلي يرفض بـ409.

## قيود

- `Ordering` الجزئي يحسب المواضع الصحيحة فقط (لا يراعي الأزواج النسبية) — مقبول كسياسة تصحيح أولى وقابل للتغيير دون تغيير الواجهة.
- settle-on-request يعني أن محاولة منتهية الوقت بلا تفاعل تبقى `InProgress` حتى أول طلب لاحق — لا أثر وظيفي لأن النتيجة تُسوّى عند القراءة.
